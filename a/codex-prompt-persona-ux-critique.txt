## Your task — DO NOT WRITE OR MODIFY ANY CODE

You are being asked to produce a written critique only, roleplaying as two distinct real
travellers looking at this exact screen for the first time on a phone, mid-trip-planning,
under time pressure. Do not jump to implementation. Output a single markdown document.

### Persona 1 — Priya, the price-conscious backpacker

- Budget-constrained, comparing every option by price first, willing to accept less
  convenient times if it saves money.
- Has used budget OTA apps (Skyscanner, AirAsia app, 12Go) before and expects sort-by-price
  and filter controls as table stakes.
- Gets frustrated by having to manually scan 20 unsorted rows to find the cheapest one.

### Persona 2 — Marcus, the time-conscious business-adjacent traveller

- Has 90 seconds on his phone between meetings to make a decision, not for browsing.
- Wants the app to make the decision easy, not comprehensive — one clear recommendation,
  minimal taps, minimal scrolling.
- Actively dislikes seeing 20 near-identical rows and having to click twice per option
  (Verify, then Switch).

## Required output structure

Write `docs/persona-ux-critique-2026-08-26.md` with these sections:

### 1. Priya's walkthrough (price-conscious)
In first person, narrate exactly what she sees, in what order, and where she gets stuck or
irritated, referencing the actual screen content above line by line where relevant. End with
her top 3 specific frustrations, ranked.

### 2. Marcus's walkthrough (time-conscious)
Same format, first person, referencing actual screen content, ending with his top 3 specific
frustrations, ranked.

### 3. Shared pain points
Cross-reference both personas' frustrations and identify which issues affect BOTH (these are
the highest-priority fixes) versus which are persona-specific.

### 4. Concrete, prioritized improvement list
For each recommended improvement, state:
- What it is, in one sentence.
- Which persona(s) it serves.
- Why it's derivable from real data already present (no fabrication) — reference the exact
  field it would sort/filter/badge by (price, departureTime, verify status).
- Rough effort tier: Small (pure UI reorder/sort), Medium (new component/state), Large
  (behavior change to Verify/Switch flow).

Cover at minimum:
- Default sort order for the 20-offer list (and why price-ascending is the sensible default
  given both personas skew price- or speed-of-decision-oriented, not luxury-oriented).
- Reducing the always-visible offer count (collapse-by-default + expand), consistent with
  the pattern already used for the 5-card verified-preview sections — do not invent a new
  pattern if reusing the existing one solves it.
- Whether "Verify offer" and "Switch to this plan" should be combined into fewer taps, and
  under what safety condition that would still be acceptable (no auto-booking, still
  requires explicit confirmation).
- What to do about the RECOMMENDED card's blank "Arrival impact" and missing first-leg
  preview data — should it be de-emphasized, relabeled, or paired with a "why this is
  incomplete" note so it doesn't look broken to either persona.
- Any quick-glance visual aid (badge, highlight, sort default) that would let either persona
  make a decision without reading all 20 rows.

### 5. What NOT to change
List anything in the current screen that already works well for one or both personas and
should be left alone, so a future implementation pass doesn't accidentally regress it (e.g.
the individually-verified SIN->BKK cards, the "no booking/payment" footer, the Keep/Switch
framing itself).
