## What StitchCheck is (read this first)

StitchCheck is a hackathon project: a traveller uploads a flight screenshot (or uses a
built-in sample itinerary), the app extracts the itinerary, evaluates whether a self-transfer
connection is at risk of failing, and shows real flight alternatives sourced live from the
Atlas Sandbox flight-search API — all strictly read-only. The app NEVER books, pays, or
issues a ticket; every screen ends with "No booking, payment, reservation, or order created."
The traveller's only actions are "Keep current itinerary" or "Switch to this plan" (which
just submits a non-binding request, not an actual booking).

Core architecture, so you have real file anchors (paths are relative to the app root — locate
the actual current filenames yourself if these have moved, they may not be 100% exact):
- `app/src/App.tsx` — main screen/step orchestration (Welcome → Review → Options/Answer →
  Done).
- `app/src/components/AlternativesPanel.tsx` (or similarly named live-alternatives component)
  — renders the "Live Atlas alternatives (N)" list, currently unsorted.
- `app/src/components/UnbookedTicketPreviewLegSection.tsx` — renders the per-leg "Verified
  unbooked previews" sections (already has a "best option + See more verified options (N)"
  collapse pattern implemented).
- `app/src/atlas/unbooked-previews.ts` — contains `BEST_OPTION_SELECTION_RULE` and
  `selectBestOptionCard`, the existing deterministic "pick the best offer" logic for the
  preview sections (NOT yet applied to the raw 20-offer alternatives list).
- `app/src/lib/atlasClient.ts` / `app/src/lib/atlasAdapter.ts` — typed Atlas Search/Verify
  client and adapter mapping raw offers to UI types (fields include `totalPrice`, `currency`,
  `departureTime`, `arrivalTime`, `carrier`, `flightNumber`, `bookable`/availability status).
- `docs/how-the-app-works-live-walkthrough-2026-08-26.md` — an existing screen-by-screen
  walkthrough doc from a live captured session, useful as ground truth for what each screen
  actually shows today.
- `docs/persona-ux-critique-2026-08-26.md` — if this file already exists from a prior pass,
  read it first and build on/refine it rather than duplicating from scratch.

Existing safety/UX rules already enforced elsewhere in the codebase that your recommendations
MUST respect (do not suggest anything that violates these):
- No fabricated data — any sort, filter, or badge must derive from real fields already
  returned by Atlas (price, time, verify status), never an invented composite score without
  showing its exact formula.
- No permanent hiding of data — any "top N by default" pattern must have a working "show
  all" expand, per the existing pattern in `UnbookedTicketPreviewLegSection.tsx`.
- No claim of "Booked" or "Switched" anywhere without a real verified outcome — "Switch to
  this plan" only ever results in "Request submitted, awaiting verified supplier outcome."
- Compact provider-status bar ("Live checks: N of 3 passed") with detail hidden behind "How
  this works" — raw provider names (MiniMax, Nosana, Atlas) must not appear in the primary
  flow text.

## Step 2 — Roleplay as two personas, grounded in what you just saw

### Persona 1 — Priya, price-conscious backpacker
Budget-constrained, compares every option by price first, has used Skyscanner/AirAsia/12Go
before and expects sort-by-price as a baseline feature. Gets frustrated scanning an unsorted
list of many rows to manually find the cheapest.

### Persona 2 — Marcus, time-pressed traveller
Has about 90 seconds on his phone between commitments. Wants one clear recommendation with
minimal taps and minimal scrolling, not a comprehensive comparison table. Dislikes two-step
interactions (Verify, then Switch) per offer.

For each persona, write a first-person walkthrough narrating exactly what they see, in order,
referencing the REAL screen content you observed in Step 1 (exact prices, carriers, offer
counts — not placeholders), and where they get stuck or irritated. End each with their top 3
ranked frustrations.
