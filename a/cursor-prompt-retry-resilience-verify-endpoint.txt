# StitchCheck — Extend Automatic Retry-with-Backoff to the Verify Endpoint
# Cursor Agent — addendum to the Search-endpoint retry-resilience work. A third Atlas call
# site was found: the "Verify and select plan" button hits Atlas Verify directly, and is
# NOT covered by the earlier retry-resilience prompt (which only covered the two Search call
# sites). Extend the same bounded, honest retry treatment here.

## Confirmed reproduction (just observed)

On the raw "Live Atlas alternatives" list, selecting a leg (e.g. GEM-02 fixture, both legs),
clicking "Verify and select plan" on a real offer (KUL → BKK, 1-stop, TR TR457, USD 77.76,
offer `off_7d072a862691d1dd9d6d3dcf`) produced:

```text
Verify: error (SERVICE_TEMPORARILY_UNAVAILABLE)
Service temporarily unavailable
```

This is the SAME transient Atlas CLI error code seen on Search calls all session — now
confirmed to also occur on Verify calls. This is honest, correct failure-handling behavior
(no silent selection occurred, per the existing safety gate) — it just needs the same
automatic-retry resilience already being added to Search, so a transient failure here doesn't
require a manual re-click during a demo either.

## Absolute constraints

- Do not weaken the existing safety gate: selection must still only happen after a genuinely
  successful Verify response. Retries must happen BEFORE reporting failure to the user, not
  as a way to eventually accept a failed result as success.
- Do not touch the Search-side retry work already specified in the prior prompt — this is
  additive, covering the separate Verify call path.
- Do not touch Nosana, extraction, or route-continuity logic.
- Do not weaken any existing test.
- Do not touch video/narration/subtitle files. Do not commit/push.

## Step 2 — Add bounded automatic retry, consistent with the Search-side fix

1. Classify `SERVICE_TEMPORARILY_UNAVAILABLE` and `SECURE_STORE_UNAVAILABLE` as retryable for
   the Verify call, same as done for Search.
2. Use the same bounded attempt count and backoff timing already established for Search (2-3
   total attempts, exponential backoff, capped around 8-10 seconds total) — reuse the same
   retry helper/utility if one was created for the Search fix, rather than duplicating logic.
3. While retrying, the "Verify and select plan" button should show an honest in-progress
   state (e.g. "Verifying…" or reuse whatever loading copy already exists for this action)
   rather than immediately showing the error on the first failed attempt.
4. Only after all automatic retries are exhausted, show the current honest error state
   exactly as today (`Verify: error (SERVICE_TEMPORARILY_UNAVAILABLE)` / "Service temporarily
   unavailable"), with whatever manual retry affordance already exists for this action.
5. Selection must still only occur on an eventual genuine success — if all retries fail,
   selection must not happen, exactly as today.
